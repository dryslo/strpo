# Лабораторная работа №5. Средства управления проектами.

## Этапы выполнения работы

### Создание и настройка проекта

1. В моём репозитории `tictactoe-course` создан новый проект GitHub Projects
   (тип Canbas) с названием **«Курсовая: Крестики-нолики»**, посвящённый
   разработке курсовой работы. Преподаватель добавлен в качестве
   коллаборатора с правами на просмотр и редактирование проекта.

2. Настроены этапы (статусы) задач так, чтобы реализовать требуемый рабочий
   процесс:
   - **Backlog** - задача сформулирована (хотя бы частично), но делать её
     пока не нужно;
   - **Ready** - принято решение, что задача должна быть выполнена в
     ближайшее время, исполнитель ещё не приступил;
   - **In Progress** - исполнитель взялся за задачу и работает над ней;
   - **In Review** - работа над задачей завершена, задача переведена на
     согласование/защиту;
   - **Done** - задача согласована и закрыта.

   Если по итогам ревью задача требует доработки, она возвращается из
   **In Review** обратно в **In Progress**.

3. В задачи добавлены два встроенных поля типа *Date* - `Start date` и
   `End date` - для указания предполагаемых дат начала и окончания работы.
   Изначально я пытался создать собственные поля с такими же именами, но
   GitHub сообщил, что эти имена зарезервированы, и предложил включить
   встроенные поля через раздел настроек view, что я и сделал.

4. Добавлено собственное поле типа *Single select* с именем `Type`, которое
   отражает тип работы:
   - **Research** - исследовательская работа;
   - **Documentation** - составление документации;
   - **Development** - программирование.

### Планирование работ по курсовой работе

Курсовая работа посвящена разработке бота-игрока для игры в «Крестики-нолики»
до 5 в ряд на поле 20×20 с препятствиями. Работа над курсовой декомпозирована
на следующие задачи, каждая из которых рассчитана примерно на 4–10 часов:

| № | Название задачи | Описание и ожидаемые артефакты | Тип |
|---|---|---|---|
| 1 | Изучение задания и постановка задачи | Разобрать README репозитория, выписать параметры игры (размер поля, длина линии, параметры препятствий), сформулировать требования к боту. Артефакт: раздел «Постановка задачи» в черновике отчёта. | Research |
| 2 | Изучение существующих алгоритмов | Найти и выбрать подходы к игре в крестики-нолики «k в ряд»: эвристики оценки позиции, минимакс с альфа-бета-отсечением, threat-space search. Артефакт: обзор алгоритмов с источниками. | Research |
| 3 | Развёртывание проекта и сборка | Склонировать репозиторий, установить CMake и зависимости, собрать проект, запустить тесты с базовым игроком. Артефакт: рабочая сборка в `build/` и записи о настройке окружения. | Development |
| 4 | Разработка алгоритма игрока | Сформулировать словесно/математически алгоритм бота, не привязанный к C++. Артефакт: раздел «Математическое описание» в черновике отчёта. | Documentation |
| 5 | Согласование алгоритма с преподавателем | Защитить алгоритм у преподавателя, внести правки. Артефакт: одобренная версия алгоритма. | Documentation |
| 6 | Реализация интерфейса `IPlayer` | Реализовать класс игрока в `tttplayer`, встроить в проект так, чтобы собирались тесты `test_my_player`. Артефакт: исходный код игрока. | Development |
| 7 | Реализация ядра алгоритма | Запрограммировать оценочную функцию и поиск хода в соответствии с разработанным алгоритмом. Артефакт: рабочий код, проходящий базовые тесты. | Development |
| 8 | Тестирование против базовых игроков | Прогнать серию игр против простого и базового игрока, замерить процент побед. Артефакт: таблица результатов в отчёте. | Development |
| 9 | Защита реализации | Продемонстрировать преподавателю работу бота, показать соответствие реализации алгоритму. Артефакт: одобренный pull request. | Documentation |
| 10 | Подготовка отчёта | Оформить все разделы отчёта согласно требованиям (введение, постановка, мат. описание, реализация, результаты, заключение, литература, приложение). Артефакт: PDF отчёта формата A4. | Documentation |

Каждая задача оформлена как **Issue** в репозитории `tictactoe-course` и
добавлена в проект. Для каждой задачи проставлены поля `Type`, `Start date`
и `End date` с примерными сроками.

Между задачами заданы зависимости (через секцию «Development» / sub-issues
и упоминания `Depends on #N` в описании):

- задача 2 зависит от задачи 1;
- задача 4 зависит от задач 1 и 2;
- задача 5 зависит от задачи 4;
- задача 6 зависит от задачи 3;
- задача 7 зависит от задач 5 и 6;
- задача 8 зависит от задачи 7;
- задача 9 зависит от задачи 8;
- задача 10 зависит от задач 8 и 9.

### Выполнение задачи
 
Для демонстрации работы выбрана задача **«Изучение задания и постановка
задачи»** (Issue #1) - она имеет результатом текстовый артефакт
(постановку задачи) и требует согласования с преподавателем.
 
Шаги выполнения:
 
1. Issue #1 переведён со статуса **Backlog** в **Ready**, затем в
   **In Progress** в момент начала работы.
2. От ветки `master` создана ветка `feature/problem-statement`, в неё
   добавлен файл `docs/problem-statement.md` с черновиком постановки
   задачи.
3. Сделан первый коммит и открыт **черновой запрос на слияние (Draft
   PR)**, привязанный к Issue #1 через ключевое слово `Closes #1` в
   описании. Связь PR ↔ Issue видна в правой панели Issue в блоке
   *Development*.
4. Преподаватель добавлен в PR в качестве **reviewer**.
> **Примечание.** Преподаватель пока не принял приглашение в репозиторий
> и проект, поэтому был отмечен в качестве ревьювера «условно». После
> принятия приглашения процесс ревью пройдёт штатно.
5. Когда работа над текстом постановки была завершена, тикет переведён
   в статус **In Review**, а Draft PR - в состояние **Ready for review**.
6. По итогам ревью тикет двигается между **In Review** и **In Progress**
   в зависимости от наличия замечаний; после принятия PR задача
   переводится в **Done**, а Issue #1 автоматически закрывается слиянием
   (благодаря `Closes #1` в описании PR), и карточка на доске
   автоматически перемещается в колонку **Done**.

 
### Исследование альтернатив
 
Помимо GitHub Projects существует множество решений для управления задачами
с похожей моделью workflow.
В качестве альтернативы для подробного рассмотрения выбран **Todoist**.
 
#### Todoist
 

Todoist - task-менеджер, ориентированный на индивидуальную продуктивность
и небольшие команды. Поддерживает проекты с подзадачами, представления
«список» и «доска», метки, фильтры и приоритеты, кросс-платформенность
(Web, Windows, macOS, Linux, iOS, Android).
 
**Тарифы (апрель 2026):** Free - до 5 активных проектов и 5 коллабораторов
на проект. 
Pro - 5€ за пользователя в месяц, до 300 проектов и 25
коллабораторов, расширенные фильтры и календарь.
 
**Ключевые ограничения:** нет встроенных зависимостей
между задачами, нет интеграции с pull-request-ами и код-ревью, в
бесплатном плане только 5 проектов.
 
**Реализация лабораторной работы в Todoist.** Создаётся проект «Курсовая:
Крестики-нолики», в нём через **Board view** настраиваются секции-колонки
`Backlog → Ready → In Progress → In Review → Done`. Тип работы моделируется
метками `@research`, `@documentation`, `@development`. Сроки задаются через
поле **Due date** (отдельного «Start date» в Todoist нет - его можно
эмулировать меткой вида `start:YYYY-MM-DD`). Десять задач курсовой
создаются как отдельные задачи; зависимости приходится отмечать косвенно -
ссылками в описании (`Depends on: <ссылка>`) и приоритетами. Поскольку
Todoist не связан с pull-request-ами, текстовые артефакты (постановка,
алгоритм, код) хранятся в Git-репозитории, а в задаче указывается ссылка
на них. Перевод задачи в `In Review` означает отправку документа
преподавателю; обсуждение замечаний идёт в комментариях задачи (доступны
на тарифе Pro).
 
Todoist подходит для упрощённой реализации этого процесса, но из-за
отсутствия зависимостей, ревью и интеграции с PR его удобство для
разработческих курсовых заметно ниже, чем у GitHub Projects.
